`enum v4l2_ctrl_type`. The second DO-NOT-UPSTREAM commit (`ec82f3807`) handles them the same way
as the H.264 one:
- The core and its KUnit test use `p_cur.p` instead of the union members.
- `V4L2_CTRL_TYPE_HEVC_ENCODE_PARAMS` (0x0277) and `_FEEDBACK` (0x0278) are `#define`s outside

### Flow per picture (HEVC)

1. `device_run` applies the request controls, copies the timestamp and calls `ops->run`.
2. `rkvenc_hevc_run()`:
   1. `v4l2_hevc_enc_step()` writes AUD/VPS/SPS/PPS through the CPU mapping (CAPTURE is MMAP
      dma-contig).
   2. `hdr_bytes = enc->header_size`. This can be 0 for a P picture without parameter sets.
      `adr_bsbs` = base + hdr_bytes.
   3. The common setup runs (source, ring and so on). Then the HEVC syntax, the references, the
      ME, the tuning and the RC are programmed. `tile_cfg` (0x3f0, which is `sli_cfg` for H.264)
      is cleared, so `tile_en` = 0.
3. In the IRQ thread, `rkvenc_hevc_done()`:
   1. sets payload = hdr + `bs_lgth`;
   2. builds `struct v4l2_stateless_encode_stats`;
   3. calls `v4l2_hevc_enc_complete()`, which does the DPB update, the TemporalId patch, the
      buffer flags, the feedback control and `rc_ops->complete`.

   `rkvenc_job_finish()` then calls `v4l2_ctrl_request_complete()` (after `complete()`, so the
   feedback is captured) and completes CAPTURE before OUTPUT (the H.264 board fix).

   On an error, an overflow or a timeout, `complete()` is not called. The DPB stays as it was,
   and the core re-sends the parameter sets on the next run.

### Constraints and accommodation (`state_constrain`)

The hardware has no registers for the coding structure, so the SPS must match what it does
(values from MPP `h265e_ps.c`):

| Element | Value |
|---|---|
| CTB / min CB | 64 / 8 (`log2_min_cb_minus3` = 0, diff = 3). `pic_{width,height}_in_luma_samples` = size aligned to 8, recomputed together with the conformance window (right/bottom) |
| TB | 4..32, `max_transform_hierarchy_depth_inter/intra` = **0**. MPP's "TU depth 1" is HM's `QuadtreeTUMaxDepth`, which HM codes as depth − 1. Signalling 1 makes decoders misparse the residual (found on the board) |
| Off | AMP, PCM, scaling lists, separate colour planes, bit depth > 8 (Main only, see Main10 below) |
| PPS off | dependent slices, constrained intra, transform skip, transquant bypass, tiles, WPP, lists modification, slice header extension, slice chroma QP offsets, extra slice header bits, `log2_parallel_merge_level` > 2 |
| PPS forced | `cu_qp_delta_enabled` = 1 (MPP always sets it, and row RC/AQ need it), `diff_cu_qp_delta_depth` ≤ 2 (2-bit field), `pps_cr_qp_offset` = `pps_cb_qp_offset` (one chroma offset register, as in MPP) |
| Slice | MaxNumMergeCand ≤ 3 (`max_mrg_cnd` is 2 bits; MPP uses 2). TMVP is cleared when the SPS has long-term pictures, as in MPP. SAO/TMVP slice flags are also masked by the *active* SPS when the registers are programmed (see open problem 5) |
| Core settings | `max_l0_refs = 1`; `rps_limits = {4 negative, 0 positive, 3 long-term}`; flags `INTER_PRED | HW_SLICE_HEADER` (no `HW_TEMPORAL_ID`: the core patches TemporalId) |

### Buffers

These are driver-internal and allocated by the core through `rec_buffer_alloc`. For each slot:
- FBC header `ALIGN(cw·ch·64, 8K)` and body `cw·ch·4096·3/2` in one buffer;
- thumbnail `cw·ch·256`;
- collocated MVs `cw·ch·96`.

Here cw = ⌈w/64⌉ and ch = ⌈h/64⌉ + 1. The flag `colmv_valid` marks whether the MVs were stored.
One extra buffer holds the current picture. The core swaps buffers between slots, so the driver
never caches slot indices.

### Rate control

- Fixed QP and CQ come from the core: I/P QP controls; CQ maps quality linearly onto
  [min, max] QP.
- **CBR** (`rkvenc_hevc_rc_*`):
  - nominal bits = bitrate × frame interval;
  - target = nominal − (accumulated error)/8, clamped to [nominal/4, 2·nominal], ×4 for I;
  - the initial I QP comes from bits per pixel, and P starts at I + 2;
  - after each picture, QP(type) = frame QP + clamp(round(6·log2(bits/target)), ±4), within
    [min, max]; P is kept within [I − 2, I + 6].
- Per the H.264 board finding, the model uses the **frame** QP, never the hardware average,
  which AQ keeps below it. The per-picture target drives the CTU row RC. Setting
  `row_rc_qp_range=0` disables the row RC and leaves frame-level RC only.

### Feedback

`V4L2_CID_STATELESS_HEVC_ENCODE_FEEDBACK`. The core fills `timestamp`, `poc`, `nal_unit_type`,
`slice_qp`, `ref_idx_l0`, `header_size` and `flags`. The driver adds `stats`:

| Field | Source |
|---|---|
| flags | QP, SSE_LUMA, BLOCKS (no skip count) |
| `qp_sum` | `st_qp_sum` |
| `qp_count` | CTUs × 64 (MPP's divisor) |
| `qp_min/max` | lowest and highest non-zero bin of `st_b8_qp[52]` |
| `sse_luma` | `sse_h32 << 16 \| sse_l16` |
| intra blocks | i32·16 + i16·4 + i8 + i4, in 8×8 units; MPP weights i4 like i8 |
| inter blocks | p64·64 + p32·16 + p16·4 + p8 |

`V4L2_CID_MPEG_VIDEO_AVERAGE_QP` is set as well.

| Kind | Controls |
|---|---|
| Stateless compound | `HEVC_SPS`, `HEVC_PPS`, `HEVC_ENCODE_PARAMS`, `HEVC_ENCODE_FEEDBACK` (read-only) |

### Not done / limitations

- **Main10.** Not possible: VEPU580 has no 10-bit input format and no 10-bit output (MPP: 8-bit
  only). The profile menu is Main only.
- B pictures, tiles (and so width > 4096), multi-slice, WPP, scaling lists (the custom table
  layout is not decoded), ROI/qpmap, DCHS frame-parallel encoding of one stream, and
  `MAIN_STILL_PICTURE`.
- Long-term references: supported by the register mapping (up to 3, with MSB cycles) and
  exercised by the client's `-L` mode, but TMVP is disabled with them.

## Test client and plan

`tools/rkvenc-enc.c` is the H.264 client plus an HEVC mode: `-e hevc`, with `-t` TMVP, `-S` no
SAO, and `-L` long-term reference. It reads NV12 and writes Annex-B `.h265`.
- SPS: `log2_max_poc_lsb_minus4` 4, DPB 2 (3 with `-L`), strong intra smoothing, SAO.
- PPS: loop filter across slices, cu_qp_delta.
- IDR_W_RADL every `-g` pictures, otherwise TRAIL_R P pictures with `refs[0]` = the previous
  picture's timestamp (USED_BY_CURR_PIC).
- With `-L`, the IDR is kept as a long-term picture, and every even picture is predicted from it.
- After each request completes, it reads FEEDBACK from the request and checks the timestamp, the
  POC, `num_ref_idx_l0_active` = 1 and the expected `ref_idx_l0[0]`. It prints
  `feedback errors: N`.

`tools/run-tests-hevc.sh <bindir> <workdir>` runs safe tests only. Inputs are ffmpeg
`testsrc2` NV12.

slightly lower PSNR, roughly equal efficiency on this synthetic content. RD tuning and natural
content are follow-ups.

### The bug found on the board

Run 1 (`board-run1.txt`) produced streams that ffmpeg parsed, mostly without errors, but that
decoded to about 6 dB (structured garbage), with occasional "cu_qp_delta out of range".

The hardware's own SSE showed about 48 dB, so the encoder's reconstruction was fine, and the
mismatch was in how the decoder interprets the CTU syntax. Rewriting only the SPS of the existing
streams on the host (`tools/sps_patch.py`, which uses the uAPI agent's reference parser and
writer) narrowed it down:

| SPS change | Result |
|---|---|
| default scaling lists | no change |
| intra depth 0 | I pictures fixed |
| inter and intra depth 0 | **every stream clean**, with the same PSNR as run 2 |

The driver now forces 0. The sign-data-hiding register was also checked: the stream is
identical with it set.

The fault tests (forced overflow, watchdog) and rmmod are still deferred, as for H.264.

## Open problems and risks

1. **Confirmed on hardware:** the syntax register layout (VPS/SPS/PPS written by the core plus
   hardware slice headers decode in ffmpeg), the inline RPS, long-term pictures, TMVP with
   colmv store/load, `max_mrg_cnd` = MaxNumMergeCand, flat quantisation with an all-zero SCL
   block and `scl_lst_sel` = 0, the HEVC tuning blocks, the row RC, and the statistics units
   (32400 intra 8x8 blocks = 1920·1080/64 on an I picture).

   **Not exercised:** the error, reset and IOMMU-recovery paths (deliberately deferred), `pic_out_flg`
   (`output_flag_present` = 0 in all tests), non-zero chroma QP offsets, deblocking overrides,
   cabac_init, and TemporalId > 0 (the core's patch path).

   The original pre-board risk list follows, for reference:
   - The HEVC syntax register bit positions are from MPP's header via a summarising fetch.
     Field widths add up to 32 in every register, but nothing has been tested.
   - `max_mrg_cnd` is assumed to be MaxNumMergeCand: it is a 2-bit field, and MPP uses 2. If
     the hardware writes a different `five_minus_max_num_merge_cand` than the core expects,
     decoders desync from the first P frame; check `-v` output with `ffprobe -show_frames`.
   - `pic_out_flg` polarity, and whether the single chroma-offset register covers Cr.
   - Flat quantisation with `scl_lst_sel` = 0 and an all-zero SCL block. If PSNR is far too low
     or the output is garbage, the SCL table needs flat entries (0x1000 Q, 0x10 IQ: MPP's
     default-list table layout).
   - The colmv store/load policy (MPP: no store on intra pictures).
   - `ltm_idx0l0` semantics: set when the l0[0] reference is long-term. MPP sets it from the SPS
     long-term flag.
2. **Statistics.** `qp_count` (CTUs × 64) and the `st_pnum_i4` weighting follow MPP's formulas.
   The units aren't documented.
3. **CBR** is a simple driver-side model. The core has no shared RC: Paul's is typed on H.264
   (open question 9.3 of the uAPI design). Tuning needs hardware results.
4. **ffmpeg probe note.** `run-tests-hevc.sh` counts ffmpeg warnings. The 4K files (60 frames)
   print a single "not enough frames to estimate rate" probe note, which is not an error.
5. **Core observation** (not changed here): `prepare_encode()` checks the slice SAO/TMVP flags
   against the SPS of the *controls*, while a changed SPS only becomes active at the next IRAP.
   The driver masks the flags with the active SPS when it programs the registers. The core
   should do that itself (report it to the uAPI author).
6. The ME window for HEVC reuses the H.264 clamp. MPP derives HEVC ranges from `merangx/y` =
   384/256 with size-dependent clamps; the final values for large pictures (11/7) agree.
7. All the H.264 driver's open problems still apply: unbind with open file handles,
   MAINTAINERS, the Collabora/Vulkan plan. Nothing is to be upstreamed before that is settled.
